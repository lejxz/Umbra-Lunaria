## Work Completed

### Roster service (`lib/planning/roster-service.ts`)
- `validateRoster(input, requireFull)` — pure validation: warSize must be one
  of the 7 allowed sizes; slot count ≤ warSize (or `=== warSize` when
  `requireFull` for finalize); map positions are 1..warSize, unique, integer;
  player tags non-empty and unique. Returns per-field `[{path, message}]`.
- `createRoster` — inserts the roster row + slots in one pass, returns the
  created roster with slots.
- `updateRoster` — rejects finalized rosters with `ConflictError`; replaces
  slots wholesale (delete + re-insert) to keep the unique-position index
  consistent during reordering.
- `finalizeRoster` — rejects already-finalized rosters; stamps `status =
  "finalized"`, `finalizedAt = now`, and `configVersion = v<SETTINGS_VALIDATION_VERSION>`
  (the auto-select config snapshot required by docs/concept/09 §4).
- `listRosters` + `getRoster` — public reads (drafts first, then finalized).
- Typed errors (`ConflictError`, `NotFoundError`) so route handlers can map
  them to the right status code without string matching.

### API routes
- `POST /api/rosters` (protected) — create a draft. Validates, then inserts.
  Returns 201 with the roster.
- `PATCH /api/rosters` (protected) — update an existing draft by `id`. Returns
  409 if the roster is finalized.
- `GET /api/rosters` (public) — list rosters. Returns 500 on DB error (sandbox
  has no live DB; production is fine).
- `GET /api/rosters/[id]` (public) — single roster with slots. 404 when missing.
- `POST /api/rosters/[id]/finalize` (protected) — re-validates the persisted
  roster with `requireFull=true` before finalizing, so a stale client can't
  finalize an incomplete draft. 409 if already finalized.
- All write routes emit `[audit]` console lines with actor + result.

### Planner UI wiring (`components/planning/planner-shell.tsx`)
- New `SaveStatus` union: `idle | saving | saved | finalized | error` with a
  message field on error.
- `draftId` state: null until the first successful save, then Save becomes an
  update (PATCH) instead of create (POST).
- `dirty` flag: set true on any slot/size mutation, cleared on successful save.
  The Save button label cycles: "Save draft" → "Saving…" → "Saved" →
  "Save changes" (when dirty again).
- Finalize button: disabled until `draftId !== null` AND `fillCount === warSize`
  AND not already finalized. Tooltip explains why it's disabled.
- Status banners in the control bar:
  - Error: rose pill with the message (e.g. "Admin session expired — log in
    again." for 401, "Roster is finalized and cannot be edited." for 409).
  - Saved: emerald pill "Saved · draft #N" or "Unsaved changes" when dirty.
  - Finalized: purple pill "Finalized · draft #N".
- War-size selector disabled when finalized (immutable).

## Decisions Made

- **Slots replaced wholesale on update**: rather than diffing the old and new
  slot sets, `updateRoster` deletes all slots for the roster and re-inserts.
  This is simpler and keeps the unique `(rosterId, mapPosition)` index
  consistent during reordering. Roster counts are small (max 50 slots) so the
  cost is negligible.
- **Finalize re-validates from the DB**: the finalize route loads the
  persisted roster and re-runs `validateRoster(requireFull=true)` before
  finalizing, rather than trusting the client. This catches a stale client
  that tries to finalize an incomplete draft.
- **`configVersion` is a simple string**: `v<SETTINGS_VALIDATION_VERSION>`
  stamped at finalize time. docs/concept/09 §4 calls for a "score/configuration
  snapshot" — the full settings document isn't serialized here because the
  auto-select score (Step 3.2) is what consumes it, and that's future work.
  The version tag is enough to detect later config drift.
- **`updatedBy` / `finalizedBy` params logged but not stored**: the schema
  has `createdBy` but no `updatedBy` / `finalizedBy` columns. The params are
  kept on the service functions and logged via `console.info` (defense-in-depth
  alongside the route-handler audit lines) so the audit trail exists. Adding
  the columns is a future enhancement if finer-grained audit is needed.
- **No separate `/api/planning` route**: the planner context is fetched
  server-side in the page component (ISR-cached), matching the dashboard /
  members / war / capital pattern. A separate API route would only be needed
  for client-side refetch, which isn't required here.
