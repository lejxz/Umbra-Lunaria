## Work Completed

### Administrator auth (`lib/auth/`)
- `session.ts` — server-side password verification (scrypt, constant-time via
  `timingSafeEqual`), HMAC-SHA256 session token create/verify, and cookie
  helpers (Secure, HttpOnly, SameSite=Strict). Tokens carry an `exp` + nonce
  payload; expired tokens are rejected. A missing/malformed `ADMIN_PASSWORD_HASH`
  fails closed (login rejected, never throws to the caller).
- `rate-limit.ts` — pure, time-injectable sliding-window rate limiter
  (10 attempts / 10 min per IP, module-level bucket store). Extracted as a pure
  function so it's unit-testable without a server.

### Auth API routes (`app/api/auth/`)
- `login/route.ts` — POST; validates password, enforces rate limit (429 +
  Retry-After), sets session cookie. Returns 503 when auth env vars are missing.
- `logout/route.ts` — POST; clears the cookie idempotently.
- `session/route.ts` — GET; public read of `{ authenticated, configured }` so
  the client can show login/logout controls without exposing any credential.

### Runtime settings (`lib/settings/`)
- `defaults.ts` — `RuntimeSettings` type + `DEFAULT_SETTINGS` covering all 7
  groups from concept/11 (inactivity threshold, activity-score weights,
  war-select weights, confidence threshold, alert timing, feature toggles,
  display limits). Defaults mirror existing hardcoded values so Phase 2 lands
  with zero observable change. Pure `validateSettings` enforces non-negative
  weights, sum-to-1.0 (1e-4 tolerance), integer bounds, and boolean toggles.
- `runtime.ts` — `getRuntimeSettings` (DB read with 30s cache, falls back to
  defaults on cold start / corrupt row / DB error) and `saveRuntimeSettings`
  (validates then upserts with audit columns).

### Settings API route (`app/api/settings/route.ts`)
- GET (public) returns `{ settings, defaults }`.
- POST (protected) requires admin session; validates twice (defensive), stamps
  `updatedBy`, logs audit lines, returns per-field errors on invalid payloads.

## Decisions Made

- **scrypt over argon2/bcrypt**: Node's built-in `crypto.scryptSync` needs no
  external dependency, is FIPS-acceptable, and is plenty strong for a single
  shared admin credential. The hash format `scrypt$<salt>$<hash>` is simple to
  generate from a one-liner.
- **HMAC token over JWT**: we don't need JWT portability — the verifier is the
  only reader. A self-signed HMAC token is smaller, has no alg-confusion
  surface, and no header to parse.
- **Single settings document**: one jsonb row keyed `runtime_settings` rather
  than one row per setting group. Atomic read/write, simpler cache, and the
  audit columns (validationVersion, updatedAt, updatedBy) apply to the whole
  document.
- **Rate limiter is in-memory, not distributed**: acceptable for Vercel
  serverless (each warm instance throttles independently). A determined
  distributed attacker would need Upstash Redis — explicitly out of Phase 2
  scope per concept/12.
- **Defensive double-validation**: `validateSettings` runs in the route handler
  AND in `saveRuntimeSettings`. The route returns a clean 400 before touching
  the DB; the save path is the last line of defense.
