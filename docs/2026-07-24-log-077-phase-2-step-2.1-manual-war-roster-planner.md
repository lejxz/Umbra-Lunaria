## Decisions Made

- **Draft state is client-side for Step 2.1**: the planner is fully usable for
  staging a roster today; persistence (save/finalize via `/api/rosters`) is
  Step 2.2. The "Save draft" button surfaces a local confirmation so it isn't a
  dead control — Step 2.2 will wire it to `POST /api/rosters`.
- **Explicit slot model over `useSortable`**: I used `useDraggable` +
  `useDroppable` for slots rather than `@dnd-kit/sortable`'s `useSortable`.
  This makes the slot-state transitions explicit and testable (pool→slot,
  slot→pool, slot↔slot swap) rather than relying on sortable's internal index
  mutation. The trade-off is no live "shuffle" animation during drag, but the
  swap on drop is instant.
- **TH badge color ramp**: rose (TH14+), amber (TH11–13), sky (TH8–10), muted
  (TH≤7). Communicates TH weight at a glance without needing the full color
  legend the war page uses — the planner's cards are compact.
- **Member detail sheet reuse**: the dashboard variant (lazy `fetch` by
  `playerTag`) was chosen over the members-page variant (pre-loaded data)
  because the planner's member list is already large and pre-loading every
  member's full detail would be wasteful. The lazy fetch pop-in is acceptable
  for a modal opened on demand.
- **Prep-day opponent context is read-only**: per docs/concept/09, the planner
  never auto-assigns targets. The opponent panel is explicitly labeled as
  scouting context. Target assignment is a leadership decision, not a planner
  feature.
